# WESP native receiver 0.2.0

ESP32 classic, 4 MiB flash, Arduino ESP32 2.0.14, PlatformIO espressif32
6.5.0. No WLED code or WLED effects. Build never opens a serial device.

## Build and artifacts

From the repository directory:

```
python build_native_receiver.py --output-dir /absolute/path/outside/worktree
python -m unittest discover -s tests -p test_receiver_core.py
```

`receiver-firmware/manifest.json` records chip, flash size, pinned platform and
framework, and `images[]` entries with file, integer offset, byte size, SHA256.
Images: bootloader at 0x1000, partition table at 0x8000, OTA selection
`boot_app0.bin` at 0xe000, application at 0x10000. The stock esp32dev default
partition table is generated by the pinned framework. Build logs, intermediate
files and binaries live under the supplied output directory, outside Git.
There is no filesystem image. The manifest is not a command to flash hardware.

## Transport and authentication

USB UART **921600 baud**, TCP port **19447**. ROM flashing remains separate
from the application protocol. Newline-delimited JSON, maximum 8192 bytes
excluding newline; partial lines expire after 250 ms **without another byte**.
An oversized, timed-out or NUL-containing line is discarded through newline.
JSON nesting is limited to eight levels and duplicate object keys are rejected.

Every request has `op`, `id` (integer 1..2147483647) and `session` (16 lowercase
hex characters, generated freshly by the PC for each connection). The first
request must be `hello`. IDs increase within that session. A USB `hello` with
a new session permits reopening the same USB UART without resetting ESP32;
it does not clear or refresh a frame lease. TCP uses one session per socket.
After USB hello, every request includes `mac`, twelve lowercase hex characters.
Every TCP request, including hello, includes both `mac` and `token` (64 hex).
One TCP socket is accepted at a time; an unauthenticated idle socket expires
after two seconds. A slow TCP reader is disconnected without blocking output.

The first boot generates 32 random pairing bytes and stores them in NVS. `pair`
returns their 64-character hex encoding over USB only. Neither hello nor error
responses contain credentials. Pairing and changing Wi-Fi credentials are
USB-only. An already paired PC can configure LED outputs/current over TCP,
using the same MAC, token and session checks as RGB frames.

All replies contain `ok`, `id`, `mac`, `proto:1`. All successful replies include
`count`, `on`, `bri`. Errors add a fixed credential-free `error` code.

## Commands

```
{"op":"hello","id":1,"session":"0123456789abcdef"}
{"op":"pair","id":2,"session":"0123456789abcdef","mac":"680947485628"}
{"op":"configure","id":3,"session":"0123456789abcdef","mac":"680947485628","outputs":[{"gpio":2,"count":10,"order":"GRB"},{"gpio":4,"count":10,"order":"GRB"}],"max_milliamps":500}
{"op":"state","id":4,"session":"0123456789abcdef","mac":"680947485628","on":true,"bri":255}
{"op":"frame","id":5,"session":"0123456789abcdef","mac":"680947485628","count":20,"pixels":"<base64 of exactly 60 RGB bytes>"}
```

`hello` and successful `configure` additionally return `firmware:"WESP"`,
`version:"0.2.0"`, `capabilities:{wifi_configure:true}`, `outputs`,
`max_milliamps`, `watchdog_ms:1500`, and
`wifi:{configured,connected,ip,host}`. The stable host is
`wesp-<last-six-MAC-hex>.local`, with mDNS service `_wesp._tcp` port 19447.
Registration starts after Wi-Fi joins, without waiting for DNS clients.
Use the reported IP if the local network does not support mDNS.
Factory output list and count are empty/zero;
there are no default personal GPIO assignments.

Configure requires 1..8 outputs, total 1..1024 LEDs, unique GPIO from
`2,4,5,13,14,15,16,17,18,19,21,22,23,25,26,27,32,33`, positive integer count,
order `RGB/RBG/GRB/GBR/BRG/BGR`, and `max_milliamps` integer 100..5000.
The factory current budget is 500 mA. Optional
`wifi:{ssid:"...",password:"..."}` accepts SSID 1..32 UTF-8 bytes and password
8..63 bytes, or empty password for an open network. Omission preserves stored
Wi-Fi credentials. All fields validate before any persistence. Applying a
configuration first sends black to the old layout, turns the state off, clears
the frame/owner, initializes the new dark layout, then commits one NVS blob.
If output initialization or persistence fails, it restores the previous layout
and stays off. A TCP configure containing `wifi` is rejected before applying
anything; leaving it out retains SSID, password and pairing bytes unchanged.
The host confirms every successful save with a separate authenticated hello
and exact read-back of outputs/current before committing local controller state.
An explicit settings read can recover count after an ambiguous lost CFG reply;
ordinary frames and status polls retain their strict saved-count guard.
No frame causes an NVS write. Wi-Fi joining does not wait for connectivity.

`state` accepts optional `on` boolean, `bri` integer 0..255, and `color` three
integers 0..255. Color is retained as control metadata; actual output always
requires an RGB frame generated by the PC. `on:false` clears frame validity
and immediately outputs black. `on:true`, brightness/color changes, status
polls and hello never refresh the watchdog or revive cleared pixels.

`frame` requires exact configured count and canonical unpadded RGB base64:
three bytes per LED, four base64 characters per LED, no whitespace/padding.
The entire frame is validated before output. While off, valid frames are
discarded without taking an owner lease. While on, a valid frame acquires or
refreshes a lease for that transport **and session**. Another session or
transport is rejected while the current owner is fresh. Watchdog expiry clears
the buffer and releases ownership; either transport can then acquire it.
Off/disconnect and expiry cannot be reversed without a new valid frame.

TCP disconnect clears only a lease held by that TCP session. An unauthenticated
socket and old TCP sessions cannot darken USB-owned output. A classic ESP32
with an external USB-UART bridge cannot observe PC file-descriptor close;
USB loss therefore becomes dark through the frame watchdog. Its internal
expiry is 1200 ms, reserving 300 ms for bounded loop/RMT delivery within the
published 1500 ms target; physical timing still requires board verification. Wi-Fi
loss darkens a TCP-owned output immediately when the link event is observed.

## Startup and connection indication

Saved valid outputs show one dim amber runner at power-up. The first accepted
hello in a new authorized session shows one green runner; repeated status/hello
requests in the same session do not repeat it. Wi-Fi association alone is not a
WESP connection. An active frame owner suppresses a new connection indication.
Each output runs its full length in 700 ms, with a head capped at 20/255 and two
fading tail pixels. A green pass may follow an ongoing amber pass once.

These bounded cues are the only exception to ordinary darkness without PC
frames. They do not change On, raw PC pixels, frame ownership, lastFrame or the
watchdog. Incoming frames keep updating while a cue is displayed; the latest
valid frame appears afterward. Off and frame expiry cancel current and queued
cues immediately. No output pins are guessed when the configuration is empty.
The implementation uses the existing loop/RMT path, without delay or NVS writes.

Brightness is applied before a conservative 20 mA/full-scale RGB-channel
budget (60 mA/full-white pixel). Integer-floor scaling cannot exceed that
LED-only budget. RMT transmission time is bounded by the total 1024 pixels
(about 31 ms); input is processed in 512-byte chunks and socket sends never
wait for an unresponsive PC. Boot/reset initializes saved outputs dark before
starting the bounded amber indication.

## Verification boundary

Native C++ safety tests use the same core as the firmware and run under
AddressSanitizer and UndefinedBehaviorSanitizer. They cover strict RGB count
and encoding, bad pins/duplicates, current limiting, off/resume, watchdog,
owner/session isolation, USB session reopening, stale IDs and partial/oversize
line handling. Animation tests cover timing/queue expiry, different output lengths,
Off/watchdog precedence, frame retention, counter wrap and the current budget.
PlatformIO compilation verifies the actual ESP32 build.
These checks do not establish physical LED, Wi-Fi or separate-power acceptance;
those require the specifically authorized board and user-supplied Wi-Fi setup.

## Native effects extension (0.2.0)

hello adds native_effects/preview/ota capabilities, build_sha256 (ELF identity)
and ota_trial. effects, when present, is a schema1 configuration with revision,
up to128 compact [start,count,reverse] sections, up to8 presets, active preset ID,
wallpaper_timeout_ms (1500..60000), wallpaper_fade_ms (0..10000), and notification
style/color/strength/duration. Presets contain ID, meter/pulse, ten palette colors,
sensitivity50..200, gate0..30, attack_ms0..300, decay_ms80..600,
repeat_ms0 or180..5000. Configuration lives in a separate NVS key and is written
only when changed; color/audio/event runtime state stays in RAM.

effects_configure validates the complete object before persistence, echoes full
metadata, and is followed by an independent hello read-back. CFG changes neither
power nor last input time. All commands retain ordinary MAC/token/session checks.
- audio(revision,rms,bass): finite values0..1 before gain/envelope, fresh music lease.
- effect(revision,mode,color): solid or runner, fresh wallpaper-class lease.
- heartbeat(revision): renews an existing unexpired non-music lease for its owner.
- event(revision,kind,ref,value): notification, volume, clear or clear_volume.
  References are16 lowercase hex; duplicates do not restart an animation.
  Events never renew the underlying source lease. Volume has priority; a pending
  notification starts afterward while audio continues updating underneath.
- palette(revision,colors): transient ten-color palette update, no NVS write.
- preview: read current rendered RGB as base64, including brightness/current cap;
  no lease renewal. The desktop requests this only for an open live preview.

## Paired OTA extension

ota_begin(size,sha256), ordered ota_chunk(offset,data) with up to1024 decoded
bytes, ota_finish and ota_abort update only the inactive app slot. The receiver
checks exact length, SHA256 and ESP image validity before selecting it for boot.
A stalled transfer aborts after10s; output is off before flash erase begins.
USB remains available for recovery. Hardware/network/effects NVS keys are retained.

The pinned SDK enables app rollback. verifyRollbackLater is overridden so Arduino
does not confirm a candidate before WESP can validate it. A pending boot requires
explicit ota_confirm within60s, with NVS and output initialization ready. WESP
checks MAC, ELF build identity/version and unchanged outputs/effects first. A
failed/unconfirmed boot reverts to the previous slot. This mechanism still needs
physical validation against the actual installed bootloader for each supported
upgrade path; successful policy tests are not evidence of physical rollback.

## Real-time audio extension — native0.2.1

After pairing, TCP audio_open(revision) returns a RAM-only streamid/key, UDP19448
and receiver clock. audio_clock returns a small clock response; neither operation
renews lighting. Host accepts sync RTT<=80ms, refreshes5s, expires10s.
UDP40 bytes, big endian: WSA1(4),id(8),sequence(4),sampleMillis(4),RMS(2),bass(2),
HMAC-SHA256/128(16). Levels use unsigned0..65535. Require active authenticated TCP
peer, current CFG/session, increasing sequence and estimated age[-40,80]ms;
40ms clock-sync uncertainty bounds intended real age120ms. Off/config/scene/OTA/
disconnect revoke grants. No per-audio ACK, JSON parsing or NVS writes. Receive
batches render only the newest accepted input. Music loss lease stays1200ms;
rendering/repeats/history run locally at10ms. Station power-save is disabled.
The existing paired control transport remains unencrypted; this extension uses
RAM-only stream keys over that same local trust boundary. Public diagnostics
include only packet counters, ages, paint delay and authentication CPU time.
